# LinkVideo v0.27 抖音解析性能设计

## 目标

在不改变哔哩哔哩、快手、下载、预览、批量解析和 OTA 行为的前提下，缩短抖音解析的无反馈等待，并优先利用已经完成验证的浏览器身份直接走原生解析。只有原生页面数据与接口路线均无法取得目标作品时，才加载抖音官方网页。

## 已确认现状

- `VideoParser.parseDouyin` 会依次读取短链/落地页、分享页、旧详情、普通详情、匿名注册后的普通详情、签名详情，最后才进入 WebView。
- 进入 WebView 前固定上报 88%，因此 88% 代表回退阶段，不是实际完成比例。
- 默认隐藏 WebView；无进展 8 秒或总计 16 秒后才显示，冷状态验证因此被延迟。
- 每次解析创建并销毁 WebView，但 `CookieManager` 是应用级共享；当前成功后没有明确 `flush()`。
- 原生 `HttpFetcher` 不读取 `CookieManager`，所以完成验证后的身份没有主动用于下一次原生详情请求。
- 当前会把解析过程中的 Cookie 放入可序列化的媒体/图片请求头，批量草稿和 Activity 状态可能把这些值写入本地文件。

## 方案

### 原生优先路线

1. 用户点击解析后才访问该作品链接，不在应用启动或后台预取剪贴板链接。
2. 先解析短链和落地页内嵌数据；如果落地页已经是同一个规范分享页，不重复请求。
3. 从系统 `CookieManager` 读取 `https://www.douyin.com/` 当前 Cookie，仅在内存中用于同源抖音详情请求，不写日志、结果对象、草稿或 Intent。
4. 旧详情、普通详情和签名详情保持串行。明确的 HTTP 403，及旧详情 `status_code=11110`，让对应路线进入 15 分钟进程内冷却；网络中断、取消和超时不进入冷却。
5. 已有稳定身份时跳过匿名注册；没有身份时，匿名注册只有产生新的身份 Cookie 才重试普通详情。浏览器身份确实变化后只重新开放普通详情路线，保留旧接口和签名路线的失败冷却。
6. 每次解析设置 90 秒总预算；阶段间检查剩余预算，避免多层回退无限叠加。

### 浏览器回退

- 冷状态或没有浏览器身份时，一旦确定需要 WebView，立即显示验证页面，不再隐藏等待 8 秒。
- 有浏览器身份时允许最多 4 秒隐藏快速读取；脚本启动失败、详情 403 或请求超时时立即显示。
- WebView 会话结束时调用 `CookieManager.flush()`，再销毁 WebView；网页等待不超过本次解析的剩余预算。
- WebView 仍只允许受信任的抖音 HTTPS 地址，取消、超时、Activity 结束和渲染进程退出时必须清理。

### Cookie 和结果安全

- `MediaStream` 与 `ImageResource` 的可序列化请求头移除 `Cookie`、`Authorization` 和 `Proxy-Authorization`。
- 仅在应用自己控制且能逐跳检查重定向的下载或图片请求中，如实际 URL 是 `douyin.com` 或其子域，才临时从 `CookieManager` 注入 Cookie；跳转到其他域后不携带。外部浏览器和系统播放器只接收脱敏后的持久请求头。
- 诊断只记录阶段、耗时、状态码、响应形态和是否存在身份，不记录 URL 查询、正文或 Cookie 值。

## 验收

- 冷状态进入浏览器回退时立即出现清晰验证界面，不再静默卡 88% 约 8 秒。
- WebView 验证成功且 Cookie 仍有效时，下一次先携带该身份尝试原生详情；成功时完全不创建/加载 WebView。
- 同一路线明确 403/11110 后，15 分钟内其他链接不重复完整尝试；网络故障不会误伤路线。
- 同一分享页不重复拉取；匿名身份未变化不重复普通详情。
- 可序列化结果、批量草稿和诊断不含 Cookie 明文。
- 哔哩哔哩和快手行为保持不变；核心测试、浏览器脚本测试、资源处理、Java 编译、lint 和 APK 构建通过。
- 没有连接真机时，交付说明必须明确“尚未完成真机验证”。
